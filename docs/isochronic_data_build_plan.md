
## 9. 完稿侧造数：用 `x_src` 判定真实失败（2026-11-09 19:20 起）

### 9.1 转换率实测，纠正一个假设

第一版让 UND 看**预览 `P`** 写修复请求，再用完稿早筛：

| 结果 | 条数 | 占比 |
|---|---:|---:|
| 真实修复（完稿上确实为假） | 352 | 9.2% |
| **误触发（完稿本来是对的）** | **2,582** | **70%** |
| 缺保留题 | 587 | 16% |

**70% 的"预览缺陷"在完稿上不存在。** 预览只有 3 次求值，UND 对着它数杯子、判属性会误判，而这些缺陷并不延续到成图。

结论：**离线造数一律读完稿**，预览只保留为部署视图（其误判产物正是诊断器的负例）。

### 9.2 目标 20,000 条所需的量级

按 9.2% 转化率，每 6,000 条提示词约出 550 条。要到 20,000 条：

```
20,000 / 0.092 ≈ 217,000 条提示词 → 还需约 36 轮 × 6,000
```

单纯堆数量是线性的，所以同时换成**更高产出的失败族**（`build_targeted_prompts.py`）：

| 族 | 形态 | 预期更常失败的原因 |
|---|---|---|
| `crowd` | "exactly 8–14 个物体，每个都完整在画面内" | 底座普遍画少 |
| `pair` | 两个同类物体，属性需要归属正确 | 常把属性绑错主体 |
| `relation` | 明确的 left/right、above/below | 常画反 |
| `text` | "整个单词清晰可读且居中" | 常漏字或糊掉 |

### 9.3 自动多轮生成

`/tmp/repair_pool_gen.sh` 无人在环：

```
每轮：提示词 → 父轨迹(64 卡) → 完稿侧修复请求 → 完稿复核 → 入池
      轮次 uid 加后缀避免冲突；池子 ≥ 20,000 或单轮产出 < 5 即停
```

`repairgen:` 开头的行写入 `TERMINAL_STATUS.md`。定时任务每 30 分钟检查一次，
发现停滞就重启、发现某族产出低就提高该族配额、族耗尽就新增失败形态。
