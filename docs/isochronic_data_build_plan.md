## 1. 三条必须先解决的工程问题

### 1.1 几何不一致会污染监督

源图与目标图是同一场景的编辑前后。若宽高比不同（例如 832×1248 → 1024×1024），直接各自缩放到 512×512 会把"局部编辑"变成"缩放 + 编辑"——这正是第二轮修掉的 `images.py::load_pair` 问题。

**规则**：`|ratio(src) − ratio(target)| ≤ 1%` 才保留；否则用共同场景矩形裁切；无法判定就丢弃并计数。

### 1.2 RGBA 与位深

目标图可能是 RGBA。**规则**：统一白底合成 → RGB → `[-1,1]`，源与目标用同一条路径，避免"透明度变成编辑"。

### 1.3 离线归一化，不要每步解码

963 GB 原始文件在线解码会拖垮训练。**规则**：一次性预渲染 512×512 协议画布缓存（JPEG q=95 或无损），训练只读缓存。

预算：490,628 × 2 张 × ~250 KB ≈ **245 GB**；解码+缩放 98 万张，64 路并行约 **10 分钟**。若先做 5 万条试点则约 25 GB。

## 2. L 线（显式编辑对，越多越好）

**规模目标：全量 490,628 条**（几何不合格的剔除后按实际）。

| 步骤 | 做法 |
|---|---|
| 1 | 按 §1 归一化并缓存到 `L_norm/<uid>_{src,tgt}.jpg` |
| 2 | 几何门禁 + RGBA 统一 + 最小边长 ≥256 |
| 3 | 指令取 `prompt_draft`（英文，与现有条件分布一致）；长度 >60 词或含"perform these edits in order"的复合指令（T11）单独标记 |
| 4 | **`parent_condition` 需要生成**：L 的前瞻预览 `P` 要用源场景描述，池里没有。用 UND 对源图描述一次，**按源图去重，41 万次调用**，64 路并行约 **5 小时**，结果落盘复用 |
| 5 | 家庭切分：`source_family = sha1(uid)[:8]`，同一源图的多条编辑只能落在同一 split；val 取 2% |
| 6 | 输出 `L_pool.json`（manifest，字段与现 `LinearManifest` 一致） |

**分层而不是纯随机**：每个 task 设上限（例如 6 万），避免 T2 颜色类占 22% 主导梯度；T8/T9/T3 不设上限。

**与终端监督的关系**：L 的 `a = t·x_src + (1−t)·σ·ε`、目标图 `x_tgt`，损失同样是"经过尾段后的成图 vs 目标图"，不需要改代码。

## 3. R 线（真实轨迹，越多越好）

三条来源，职责不同，**不要混为一谈**：

### 3.1 R-keep「反向对冲」——零生产成本，规模最大

对池内任意一条 `(src → target)` 取**反向**方向：让模型从 `target`（已编辑完的图像）出发，去还原 `src`。

- 损失侧：`x_src = target`，`x_tgt = src`，指令固定 `"Keep the current scene unchanged."`
- 为什么有用：还原"加了 3 台笔记本"的画面，必须**移除对象并重建它遮住的背景**——正是 T3 那类破坏性重绘；还原"手在下"必须**重排两个已有对象**。
- 为什么零成本：方向翻转不改变 `b − a = t(x_tgt − x_src)` 的代数恒等式，不需要新轨迹、不需要反演。
- 规模：理论 490,628 条；建议先取 **60,000 条**，优先 T8/T9/T3，缓存约 30 GB。

### 3.2 R-edit「真实失败蒸馏」——闭环修复的主训练数据

针对 T8/T9/T3 三类，走真实 T2I 失败链路：

```
定向提示词（计数 N≥5 / 空间关系 / "不得出现 X"）
  → 原生 T2I 跑满：a、预览 P、父图完稿 x_src
  → UND 审查：指出一条具体失败 + 修正指令 e + c_tail
  → 前置校验：该要求在 x_src 上确实为假
  → 图像条件教师得 b，尾段得 x_eff
  → 验收后入库
```

- 规模目标 **1,500–3,000 条**；生产约 1 小时（64 卡）
- **训练时的指令必须由与部署相同的 UND 调用产生**，不能手写

### 3.3 R-edit「前向编辑」——广度保底

现有 `coupled_v6` 的 423 条（98% Add）保留，占比压到 10%，只做防遗忘。

### 3.4 配比（全量 L 的情况下）

| 角色 | 权重 | 来源 | 曝光（按 1,200 步 × 64） |
|---|---:|---|---:|
| L-edit | 40% | 490k 分层 | 0.06 次/条 |
| R-keep 反向 | 30% | 60k | 0.38 次/条 |
| R-edit 修复 | 25% | 1,500–3,000 | 6.4–12.8 次/条 |
| R-edit 前向 | 5% | 423 | 9.1 次/条 |

L 和 R-keep 在 40 万量级下每 epoch 远不足一次，这是**有意的**：它们的职责是广度与分布覆盖，不是把单条背下来。真正的梯度信号来自 R-edit 修复那 25%。

若要让 R-edit 修复达到 23 次/条的合格曝光，则 1,200 步下 1,500 条对应权重约 **0.45**，L 相应降到 0.20、R-keep 0.30、前向 0.05。

## 4. 缓存格式与目录

```text
$D/data_v3/
  L_norm/<uid>_src.jpg  L_norm/<uid>_tgt.jpg        # 512×512 归一化
  L_pool.json                                        # manifest
  L_captions.jsonl                                   # 源图 UND 描述，按 source_image 去重
  R_keep/            # 反向对冲：state_a + preview + (x_src=target, x_tgt=src)
  R_repair/          # 失败蒸馏：a, b, preview, x_src, x_eff, 指令, 两组问题
  R_fwd/             # 复用 coupled_v6
```

每条缓存记录带 `family, task, direction, geometry_ok, caption_source`，便于事后分层。

## 5. 门禁

| 检查 | 判据 | 不过怎么办 |
|---|---|---|
| 几何一致性 | 宽高比差 ≤1% | 丢弃并计数 |
| 归一化往返 | 归一化再读回，有效区 L1 ≤0.02 | 查缩放实现 |
| 指令可用 | 非空、≤60 词、非复合 | T11 单独标记 |
| 场景描述 | 每张源图有 caption，长度 8–60 词 | 重新描述 |
| 反向对语义 | 抽 200 条人工/UND 复核"反向确实是一次有意义的编辑" | 按 task 剔除 |

最后一条最重要：**反向对冲的有效性取决于"反向确实有意义"**。T8（加 3 台→减 3 台）成立；T1（文字替换）反向也成立；但 T6（风格化）反向近乎恒等，应剔除。

## 6. 执行顺序

| 步 | 内容 | 时长（64 卡） |
|---|---|---:|
| 1 | 几何/分辨率盘点脚本（不出图，只统计） | 0.2 h |
| 2 | 5 万条试点归一化 + manifest | 0.3 h |
| 3 | 源图 caption（按源去重，试点 3 万源） | 0.5 h |
| 4 | 反向对抽取 + 语义复核 200 条 | 0.2 h |
| 5 | 试点训练 150 步（L 全量试点 + R-keep + R-edit） | 1.3 h |
| 6 | 全量归一化 490k + caption 410k | 5.5 h |
| 7 | 主训练 1,200 步 | 10.3 h |

试点先行的理由：5 万条和 49 万条的差别不在"够不够学"，而在"会不会被几何错误和 caption 质量拖垮"。先花 2.5 小时确认前两步干净，再花 5.5 小时铺全量。

## 7. 两个需要你拍板的取舍

1. **是否全量 490k 做 L**：全量缓存 245 GB、caption 5 小时。若只要能支撑 1,200 步（每轮只用到 3 万样本），10 万条分层样本已足够，且能省 4 小时和 180 GB。**我建议先 10 万分层**，等闭环跑通再铺全量。
2. **反向对冲是否进主训练**：它是零成本的破坏性重绘信号，但"反向是否都是有意义的编辑"需要抽查。**我建议先按 T8/T9/T3/T1 四类抽 3 万条**，T6/T7/T11 排除。

## 8. 决策记录（2026-11-09 16:00，按用户决定改写）

以下三条**推翻/修正了本文前面的建议**，以此节为准。

### 8.1 反向对带真实指令，归入 L-edit，不进 R-keep

原方案把反向对写成"保持不动"是错的：反向对的终图与起点不同，用保持指令训练会教出"没有要求也可以删除主体"，与闭环里"画对就不动"直接冲突。

修正后：

| task | 反向指令写法 | 处理 |
|---|---|---|
| T8 | "Remove 3, keeping the same scene otherwise unchanged." | 保留，优先能明确"保留哪几个实例"的对 |
| T9 | "Undo the rearrangement: restore the previous spatial relation." | 保留，且只留主体身份与视角基本一致的对 |
| T3 | "Put the removed object back where it was and blend it into the scene." | **优先用正向**（原任务已是删除补背景），反向仅少量 |
| T1 | "Restore the original text in the same place, font and colour." | 可反向，优先级低于计数/删除/空间/属性 |
| T6/T7/T11 | 反向近乎恒等或复合 | **丢弃**，`reverse_instruction()` 返回 None 即剔除 |

代码：`explicit.py::reverse_instruction(task, forward_prompt)` 已实现，T8 会从正向指令里解析步数并生成"移除 N 个"或"补回 N 个"。

并且：**反向对是 L 数据（起点是线性加噪），不是 R-keep。** R-keep 必须是原生历史态 + 明确保持指令 + 该轨迹自己的完稿。两类都保留，职责不混。

### 8.2 主数据来自真实失败，不是把外部编辑对改名

外部 T8/T9 只用来提供**目标条件**（例如"画面上正好有五台笔记本电脑"），不照抄它的修复动作。生产合同改为：

1. 按原提示词跑原生 T2I → 真实 `a`、预览 `P`、原生完稿 `x_src`
2. 用**部署时同一套 UND 调用**读 `P`，提出一条针对当前画面的修复指令；用 `x_src` 确认该错误若不干预确实会留到终图（避免把前瞻预览漏画当成真实缺陷）
3. 离线用**实际被编辑的 `x_src`** 生成教师目标，沿用现有图像条件教师 + 原生尾段；自纠错尾段条件 `c_tail = c_raw`
4. 验收实际接续出的目标图：指定错误修好、原本正确的没被破坏、形体成立；高频只做纹理筛查

教师一次产出，不做多种子选优。

### 8.3 配比（1,200 步 × 64 = 76,800 次抽样）

| 数据 | 权重 | 抽样 | 职责 |
|---|---:|---:|---|
| **R-repair（真实失败修复）** | **50%** | 38,400 | 主任务，2,000–3,000 条 |
| L-edit 正向 | 20% | 15,360 | 通用编辑能力（复用已处理 ~2.9 万对） |
| L-edit 反向（带指令） | 15% | 11,520 | 补过数删除与关系重排 |
| R-keep 真实历史态 | 10% | 7,680 | 无事不改 + 误触发副作用 |
| R-edit v6 显式编辑 | 5% | 3,840 | 保留真实中间态局部添加能力 |

**R 用终端监督，L 用已有的线性状态流匹配回放。** 当前 `terminal.enabled` 是全局开关，会让 L 也走尾段；必须改成按角色选择更新路径。现有采样器只识别大类角色，`L_edit` 内正反向、`R_edit` 内修复与 v6 都要拆成独立 role 才能兑现上表。

### 8.4 L 只处理本轮用到的部分

10 万是候选池，不是开训前必须做完的缓存。先复用现有 L，再定向补 T8/T9/T3 与属性绑定。几何：宽高比接近只说明形状接近，不说明视野一致；`832×1248 → 1024×1024` 若找不到真实对应范围，**直接丢弃**，不居中裁两张凑数。翻转时源/目标场景描述互换，反向指令单独写。切分按**原始源图家族**，不是 `sha1(uid)`。

### 8.5 首批目标

首批 **1,000–1,500 条**验收通过的修复对就开正式训练；用已验证画质的终端监督检查点初始化；150 步开始出图，300 步看第一版闭环结果。交付物是**同种子两列：原生直通 / 自动反馈纠偏**，图上标明「原要求 / UND 看到了什么 / 实际怎么改」。

复用盘点（实测）：`r_v3` 有 262 条 `needs_edit`，全部带 `source_image + states`，可直接复用；现有 `coupled_explicit/sc/v4/v5/v6` 的合格对合计 427 条，其中 **410 条是 Add**——**不能**用 Add 的 78.7% 通过率反推修复数据的产量。
