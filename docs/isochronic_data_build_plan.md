
## 9. 完稿侧造数：用 `x_src` 判定真实失败（2026-11-09 19:20 起）

### 9.1 转换率实测，纠正一个假设

第一版让 UND 看**预览 `P`** 写修复请求，再用完稿早筛：

| 结果 | 条数 | 占比 |
|---|---:|---:|
| 真实修复（完稿上确实为假） | 352 | 9.2% |
| **误触发（完稿本来是对的）** | **2,582** | **70%** |
| 缺保留题 | 587 | 16% |

**70% 的"预览缺陷"在完稿上不存在。** 预览只有 3 次求值，UND 对着它数杯子、判属性会误判，而这些缺陷并不延续到成图。

结论：**离线造数一律读完稿**，预览只保留为部署视图（其误判产物正是诊断器的负例）。

### 9.2 目标 20,000 条所需的量级

按 9.2% 转化率，每 6,000 条提示词约出 550 条。要到 20,000 条：

```
20,000 / 0.092 ≈ 217,000 条提示词 → 还需约 36 轮 × 6,000
```

单纯堆数量是线性的，所以同时换成**更高产出的失败族**（`build_targeted_prompts.py`）：

| 族 | 形态 | 预期更常失败的原因 |
|---|---|---|
| `crowd` | "exactly 8–14 个物体，每个都完整在画面内" | 底座普遍画少 |
| `pair` | 两个同类物体，属性需要归属正确 | 常把属性绑错主体 |
| `relation` | 明确的 left/right、above/below | 常画反 |
| `text` | "整个单词清晰可读且居中" | 常漏字或糊掉 |

### 9.3 自动多轮生成

`/tmp/repair_pool_gen.sh` 无人在环：

```
每轮：提示词 → 父轨迹(64 卡) → 完稿侧修复请求 → 完稿复核 → 入池
      轮次 uid 加后缀避免冲突；池子 ≥ 20,000 或单轮产出 < 5 即停
```

`repairgen:` 开头的行写入 `TERMINAL_STATUS.md`。定时任务每 30 分钟检查一次，
发现停滞就重启、发现某族产出低就提高该族配额、族耗尽就新增失败形态。

## 10. 按实测产出重排提示词预算（2026-11-09 21:30）

round 2（七族各 1,500 条、生成器已修）的分族转化率：

| 族 | 真实 | 误触发 | 转化率 | 处置 |
|---|---:|---:|---:|---|
| **colour**（同形不同色） | 465 | 617 | **43.0%** | 主力，配额 5,000 |
| under（精确小计数） | 152 | 550 | 21.7% | 保留 1,500 |
| over（拥挤计数） | 167 | 727 | 18.7% | 保留 1,500 |
| attr（同形属性归属） | 160 | 863 | 15.6% | 保留 1,500 |
| space（明确方位） | 6 | 67 | 8.2% | 降到 1,000 |
| occlusion（前后遮挡） | 11 | 306 | 3.5% | 移除 |
| text（整词可读） | **0** | 1,050 | **0.0%** | 移除 |

两条结论：

1. **"两个同形物体分别染成不同颜色"是最稳定的失败构造**（43%）。底座几乎总是把两个染成同一色或第一个颜色，这是可被完稿侧审计稳定捕捉的错误。
2. **`text` 族 0/1,050 是一次有效的否定结果**：底座在"整词可读"上实际做得很好（或 UND 无法判文字对错）。继续给它配额是纯浪费，因此移出，而不是调低。

`build_targeted_prompts.py` 新增 `--quota` 按族给量，循环脚本 `repair_pool_gen_v2.sh` 用上表配额：

```
colour=5000, over=1500, under=1500, attr=1500, space=1000   （共 10,500）
```

预计每轮产出 ≈ 3,000 条（原为 1,200），从 2,301 条到 20,000 条约 **6 轮、6–7 小时**。
